# miniOpenClaw 学术研究 Agent 深度技术解构

> 本文档对 miniOpenClaw 项目中"学术研究 Agent"的架构设计进行四维深度分析，涵盖全链路作业流程、上下文管理机制、架构约束与设计范式、以及 Agent 熵减与稳定性管理。

---

## 一、全链路作业流程

### 1.1 总体生命周期

miniOpenClaw 的学术研究 Agent 遵循一条**五阶段闭环生命周期**，从需求输入到报告生成，每个阶段都有明确的状态转移逻辑：

```
需求输入 → 任务拆解 → 知识检索 → 逻辑推理 → 报告生成
   ↑                                              |
   └──────────── 反馈回路（retry-lesson-capture） ←─┘
```

### 1.2 阶段一：需求输入与意图分类

当用户消息到达 `POST /api/chat` 端点时，系统启动一条**多层预处理流水线**：

1. **安全门控（Guardian）**：`GuardianMiddleware` 在 `before_agent` 钩子中调用轻量级 LLM（默认 gpt-4.1-mini），将用户输入分类为"安全"或"危险"。若判定为危险（prompt injection、敏感信息探测、越权操作、角色扮演攻击），系统直接跳转至终止节点，返回拦截消息，整个 Agent 图被短路。

2. **意图路由**：通过系统提示词中的 Skills 快照（`SKILLS_SNAPSHOT.md`），Agent 根据用户意图自动匹配对应 Skill。核心路由逻辑如下：

| 用户意图 | 触发 Skill | 作业模式 |
|---------|-----------|---------|
| "帮我导入这篇论文" | `paper-ingest` | 10 步结构化导入 |
| "XX 方法的原理是什么" | `wiki-ask` | 4 步知识查询 |
| "有什么新的研究方向" | `ideate` | 3 阶段创意生成 |
| "检查知识库健康状态" | `wiki-lint` | 诊断 + 自动修复 |
| "搜索最新 arXiv 论文" | `quick-lookup` | Web 检索 |

3. **记忆召回预注入**：在 Agent 图执行前，根据 `MEMORY_BACKEND` 配置，系统可能已经将长期记忆上下文注入到系统提示词中（v3 模式为自动召回，v2 `always` 模式为强制注入）。

### 1.3 阶段二：任务拆解与计划生成

学术研究 Agent 采用**声明式任务拆解**而非自由推理。每个 Skill 的 `SKILL.md` 文件预定义了完整的执行计划，Agent 读取后按步骤执行。

**以论文导入（paper-ingest）为例，10 步拆解为：**

```
Step 1: register_source        → SHA-256 去重，注册原始文件
Step 2: pdf_parser             → 提取标题/摘要/作者/全文
Step 3: LLM 深度分析           → 12 维信息提取（核心问题、方法论、实验结果等）
Step 4: save_wiki_page (paper) → 生成结构化论文 Wiki 页
Step 5: save_wiki_page (entity)→ 提取概念/方法/数据集实体页
Step 6: save_wiki_page (author)→ 创建/更新作者页
Step 7: 自动 Survey 生成       → 同标签论文 ≥ 3 时自动创建 Survey 页
Step 8: 比较页建议             → 不同方法解决同一问题时建议创建 Comparison 页
Step 9: 更新交叉引用           → 维护 Wiki 链接图
Step 10: rebuild_index + log   → 重建索引 + 审计日志
```

每个步骤的状态转移是**确定性的**——前一步的输出直接作为后一步的输入，不存在分支推理。这种设计将 Agent 的自由度限制在"如何执行每一步"上，而非"下一步做什么"。

### 1.4 阶段三：知识检索与证据收集

系统在多个层级上执行知识检索：

**Wiki 知识图谱检索（QueryWikiTool）**：
- 调用 `WikiRetriever`，执行 BM25 关键词检索 + Embedding 语义检索的混合检索
- 使用 RRF（Reciprocal Rank Fusion, k=60）融合两路结果
- 中文分词使用 jieba，英文使用标准 tokenization
- 结果按类型多样性排序（paper + concept + method 优先）

**知识库检索（SearchKnowledgeBaseTool）**：
- LlamaIndex VectorStoreIndex 语义检索 + 关键词回退
- MD5 指纹变更检测，知识目录变更时自动重建索引
- 结果合并去重，按分数排序

**外部检索（FetchURLTool + Web Search）**：
- arXiv 页面抓取、外部参考链接获取
- Tavily Search API 结构化 Web 检索

### 1.5 阶段四：逻辑推理与综合分析

在检索到足够证据后，Agent 进入推理阶段。关键约束来自 `AGENTS.md` 中的引用规范：

- **源引用**（Source）：直接来自 Wiki 页面的事实，必须标注来源
- **Agent 判断**（Agent Judgment）：基于多源信息的推理，必须标注置信度（high/medium/low）
- **禁止捏造**：Wiki 无结果时必须如实说明，不得伪造引用

推理过程中，`HarnessSecurityMiddleware` 拦截每一次工具调用，检查：
1. 敏感文件路径（glob 模式匹配 `.env`、`credentials*` 等）
2. 危险命令（正则匹配 `rm -rf`、`DROP TABLE` 等）
3. 自定义规则（`config/harness_rules.yaml`，热加载）

### 1.6 阶段五：报告生成与知识结晶

**结构化输出**：Wiki 页使用 YAML frontmatter + Markdown body 的标准化格式，8 种实体类型各有必填字段（slug, title, type, created, updated, status, confidence）。

**知识结晶（Crystallization）**：`wiki-ask` Skill 的独特机制——当一次查询综合了 ≥ 3 个 Wiki 页面并产生新分析时，Agent 主动建议将回答保存为新的 Wiki 页，实现知识的增量沉淀。

**每日自动消化（Daily Digest）**：通过 APScheduler 定时任务（默认 8:00 AM），自动从 arXiv 5 个 RSS feed（cs.AI, cs.CL, cs.MA, cs.IR, cs.RO）获取新论文，经两阶段过滤（关键词 + 语义排序，余弦相似度阈值 0.3）后，执行完整消化流水线，最后通过企业微信推送通知。

## 二、上下文管理机制（Context Management）

### 2.1 记忆架构总览

miniOpenClaw 采用**三层记忆架构**，对应不同的信息留存需求：

```
┌─────────────────────────────────────────────────┐
│           L3: 长期人格记忆 (Persona)              │
│    从 L2 场景中提取的用户画像和研究偏好            │
├─────────────────────────────────────────────────┤
│           L2: 场景记忆 (Scene)                    │
│    L1 原子事实的结构化聚合                        │
├─────────────────────────────────────────────────┤
│           L1: 原子事实 (Fact)                     │
│    从对话中提取的离散知识单元                      │
├─────────────────────────────────────────────────┤
│           L0: 原始消息 (Raw Messages)             │
│    每轮对话的完整记录                              │
└─────────────────────────────────────────────────┘
```

### 2.2 短时工作记忆：上下文窗口管理

#### 2.2.1 符号化短期记忆（Context Offload）

`ContextOffloadMiddleware` 实现了 TencentDB Symbolic Short-Term Memory 的四阶段 LLM 管线（L1 → L1.5 → L2 → L3），在两个时间点操作：

**实时压缩（`wrap_tool_call` 钩子）**：每次工具调用返回时，收集 ToolPair 到缓冲区。缓冲区满 4 对或单次输出 ≥ 3000 字符时触发 L1，LLM 生成结构化摘要（≤200 字符）+ 可替换性评分（0-10）。短结果（≤500 字符）直接通过。完整结果存入 `refs/` 目录。

**`before_model` 钩子**执行两个独立操作：
- **摘要替换（瘦身）：** 当 context 使用率 ≥ 50%，按 score 将旧工具结果替换为纯文本摘要：`[Offloaded Tool Result | node: N2] Summary: ... result_ref: refs/xxx.md`
- **MMD 注入（补视图）：** 将活跃任务的 Mermaid 流程图作为 `HumanMessage` 注入对话上下文，包裹在 `<current_task_context>` 标签中

Agent 可通过 `result_ref` 路径读取完整原文——这是一种**渐进式披露（Progressive Disclosure）**模式。

#### 2.2.2 对话摘要（Summarization）

`SummarizationMiddleware` 在 `before_model` 钩子中触发：
- **触发条件**：消息数达到 50 条（可配置）
- **保留策略**：保留最近 20 条消息，其余压缩为结构化摘要
- **摘要格式**（中文）：提取会话目标、摘要、产出物、下一步

#### 2.2.3 压缩与保真的平衡

关键设计决策：**摘要仅在对话历史中生效，不影响长期记忆**。原始对话通过 `SessionManager` 持久化为 `sessions/*.json` 文件，长期记忆系统独立从中蒸馏。这意味着即使工作记忆被压缩，所有信息在长期记忆中仍然可检索。

### 2.3 长时向量记忆：三代演进

#### 2.3.1 v1：Chroma 向量检索（遗留）

- 基于 `MEMORY.md` 文件的 256 字符分块（32 字符重叠）
- MD5 指纹变更检测，文件变更时自动重建
- 纯语义检索，无关键词能力

#### 2.3.2 v2：结构化蒸馏 + 混合检索

**蒸馏流程**：
```
对话轮次 (Exchange)
    ↓
LLM 蒸馏（Distiller，支持独立低成本模型）
    ↓
结构化记忆对象 (DistilledObject)
    ├── exchange_core: 核心信息
    ├── specific_context: 具体上下文
    └── room_assignments: 分类标签（concept/method/...）
    ↓
存储至 PostgreSQL + pgvector
```

**混合检索**：
- **Dense 检索**：pgvector 向量相似度搜索
- **Keyword 检索**：BM25 关键词匹配（jieba 中文分词）
- **融合策略**：
  - RRF（Reciprocal Rank Fusion, k=60）
  - 加权求和（dense 权重 0.3, keyword 权重 0.7，可配置）

**注入模式**：
- `tool`：注册 `search_memory` 为 Agent 工具，由 Agent 自主决定何时调用
- `always`：每轮强制注入检索上下文（`[长期记忆检索结果]` 块）
- `off`：仅用于 API，不注入 Agent

#### 2.3.3 v3：四层记忆金字塔

最先进的一代，引入了**自动化记忆生命周期管理**：

**L0 录制器（L0Recorder）**：每轮对话同步写入 `l0_messages` 表，异步计算 embedding。

**流水线管理器（PipelineManager）**：
- L1 提取：每 5 轮对话或 300 秒空闲超时触发，从 L0 消息中提取原子事实，去重后入库
- L2 聚合：L1 完成后延迟 120 秒触发，将原子事实聚合为场景块
- L3 人格：累计 50 个事实后触发，从场景中生成用户人格画像
- 所有阶段以 `asyncio.create_task()` 后台执行，不阻塞响应

**召回服务（RecallService）**：
- L1/L2/L3 三层**并行召回**（`asyncio.gather()`）
- 内容截断：每条记忆最大 500 字符，总召回量最大 3000 字符
- 确保关键证据不被信息洪水稀释

### 2.4 短时与长时记忆的交互策略

```
用户消息
    │
    ├──→ [Guardian 安全门控]
    │
    ├──→ [长时记忆召回] ──→ 注入系统提示词
    │       ├── always: RecallService.recall() (L1+L2+L3 并行) 自动注入
    │       └── tool: 不注入，由 Agent 自主调用 search_memory_v3
    │
    ├──→ [Agent 推理] ──→ 工具调用 → 结果压缩
    │       └── 上下文超限时：SummarizationMiddleware 压缩对话历史
    │
    └──→ [后处理]
            ├── L0Recorder.capture() + PipelineManager.notify_conversation()
            └── HarnessReviewMiddleware 质量审查
```

**关键设计原则**：长时记忆的写入（蒸馏/提取）和读取（召回/注入）是**解耦的**。写入发生在响应之后（异步），读取发生在请求之前（同步）。这避免了"读自己刚写的内容"导致的噪声放大问题。

## 三、架构约束与设计范式

### 3.1 设计模式：Skill-Guided Plan-and-Execute + ReAct 混合

miniOpenClaw 的 Agent 并非纯粹的 ReAct（Reasoning + Acting）自由推理模式，也不是严格的 Plan-and-Execute 预规划模式，而是一种**混合范式**：

```
┌──────────────────────────────────────────────┐
│         Skill-Guided Plan (声明式)            │
│  SKILL.md 预定义: 步骤序列、工具约束、模板     │
│  → 确定性路径控制，消除任务漂移               │
├──────────────────────────────────────────────┤
│         ReAct Execution (推理式)              │
│  LangChain create_agent 工具调用循环          │
│  → 每步内部的灵活推理和工具选择               │
└──────────────────────────────────────────────┘
```

**上层（Plan）是确定性的**：Skill 文件规定了"做什么"和"用什么工具"。`paper-ingest` 的 10 步流程不允许跳步或重组。

**下层（Execute）是灵活的**：每一步内部，Agent 使用 LangChain 的 `create_agent` 进行 ReAct 风格的工具调用循环，可以根据具体内容灵活调整。

这种设计的哲学是：**在宏观层面用确定性约束抑制熵增，在微观层面保留推理灵活性**。

### 3.2 指令集约束：System Prompt 分层组装

`prompt_builder.py` 按固定顺序组装系统提示词，形成**六层指令体系**：

```
Layer 6: AGENTS.md      → 详细操作指南（工具协议、引用标准、6 种研究工作流）
Layer 5: MEMORY.md      → 长期记忆（跨会话经验积累）
Layer 4: USER.md        → 用户画像（研究兴趣、学术背景）
Layer 3: IDENTITY.md    → 人格定义（冷静、专业、直接的风格）
Layer 2: SOUL.md        → 核心价值观（知识诚实、可追溯、结构化积累）
Layer 1: SKILLS_SNAPSHOT → 可用能力清单（XML 格式快照）
```

**关键约束**：
- 每个组件截断至 20,000 字符，防止单一组件垄断上下文窗口
- `SOUL.md` 定义的"知识诚实"原则是最底层约束，不可被上层覆盖
- `AGENTS.md` 中的引用规范（Source vs Agent Judgment）是硬性要求
- 变更 workspace 文件无需重启服务，下次请求自动生效

### 3.3 工具链约束：中间件安全链

Agent 工具调用经过五层中间件过滤，顺序严格且不可调换：

```
用户输入
    │
    ▼
┌─────────────────────────────────┐
│ ① GuardianMiddleware            │  before_agent
│   → prompt injection 检测       │  可跳转至 end 节点
│   → 失败模式: closed/open       │
└─────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────┐
│ ② HarnessSecurityMiddleware     │  wrap_tool_call
│   → 敏感文件路径拦截             │  glob 模式匹配
│   → 危险命令拦截                 │  正则匹配
│   → 自定义规则                   │  YAML 热加载
└─────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────┐
│ ③ ContextOffloadMiddleware      │  before_model + wrap_tool_call
│   → 实时工具结果压缩             │  三级压缩策略
│   → 旧消息批量压缩               │  保留最近 10 轮
└─────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────┐
│ ④ SummarizationMiddleware       │  before_model
│   → 对话历史压缩                 │  50 条触发，保留 20 条
└─────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────┐
│ ⑤ HarnessReviewMiddleware       │  after_agent
│   → 质量评分 (1-10)             │  结构化 JSON 输出
│   → 幻觉风险评估                 │  low/medium/high
│   → 工具使用审计                 │  逐工具评估
└─────────────────────────────────┘
    │
    ▼
响应输出
```

**设计约束**：
- 中间件顺序不可调换——Guardian 必须在最前面（最早拦截），Review 必须在最后面（审查完整对话）
- 每个中间件实现 LangChain `AgentMiddleware` 基类的 7 个钩子子集
- 中间件之间无直接通信，通过 Agent 图的状态传递信息

### 3.4 逻辑关卡：Wiki 质量保障体系

Wiki 引擎实现了一套**三级健康检查机制**：

| 严重级别 | 检测内容 | 自动修复 |
|---------|---------|---------|
| 🔴 Red | 缺失 frontmatter、必填字段为空、无效 status | 自动补全 frontmatter |
| 🟡 Yellow | 悬空引用（指向不存在的页面）、孤立页面（无任何引用） | 提示但不自动修复 |
| 🔵 Blue | 索引与实际文件不匹配 | 自动重建索引 |

`LintWikiTool` 的 `backfill` 模式更进一步：扫描所有已导入论文，使用 LLM 提取缺失的概念/方法/数据集实体页，自动补全知识图谱。

### 3.5 Wiki 架构：Karpathy LLM Wiki 三层模型

```
Layer 1: raw/sources/     → 原始文件（PDF/MD/BibTeX），SHA-256 去重
Layer 2: wiki/            → 结构化 Wiki 页（8 种实体类型），YAML frontmatter
Layer 3: workspace/       → Agent 指令层（SOUL/IDENTITY/USER/AGENTS）
```

**正向链接必须同步写入反向链接**：这是 Wiki 引擎的核心不变量。当论文 A 引用概念 B 时，概念 B 的"被引用"列表也必须同步更新。

## 四、Agent 熵减与稳定性管理

### 4.1 熵增问题的本质

在长链推理中，Agent 面临两类熵增：

1. **任务漂移（Task Drift）**：Agent 偏离原始目标，执行无关操作
2. **幻觉（Hallucination）**：Agent 生成与事实不符的内容，尤其是虚构引用

miniOpenClaw 通过**多层自反馈纠错机制**抑制这两类熵增。

### 4.2 确定性路径控制

**Skill 预定义工作流**是最强的熵减手段。通过将复杂任务拆解为固定步骤序列，Agent 的行为空间被从"无限可能"压缩为"有限选择"。

以 `ideate` Skill 为例，创意生成被约束为四条确定性路径：
- Path A: Gap-Driven（从研究空白出发）
- Path B: Incremental（改进现有方法）
- Path C: Combination（融合两种方法）
- Path D: Cross-Pollination（跨领域迁移）

每条路径生成 1-2 个候选想法，总计 4-8 个。Agent 不可能"天马行空"地产生与知识库无关的想法。

**Ideation Banlist（禁止列表）**：已保存的想法（无论 `proposed`、`rejected` 还是 `abandoned`）构成一个反向约束：
- `rejected`：绝对禁止再次生成
- `proposed`：避免相似度高的重复
- `abandoned`：需要明确理由才能重新考虑

### 4.3 幻觉抑制的六重防线

```
防线 1: SOUL.md "知识诚实" 原则
    → 底层价值观约束，不可覆盖

防线 2: AGENTS.md 引用规范
    → Source vs Agent Judgment + 置信度标注

防线 3: 分析提示词反幻觉指令
    → "Be factual language. If unsure, mark with [confidence: low]"
    → "Do NOT fabricate details not in the paper"

防线 4: Wiki-ask Skill 硬约束
    → Wiki 无结果时必须如实说明，不得伪造引用

防线 5: HarnessReviewMiddleware 事后审查
    → 每轮对话后 LLM 评估 hallucination_risk (low/medium/high)
    → 质量评分 (1-10) + 问题列表 + 工具审计

防线 6: Guardian 前置拦截
    → 阻止 prompt injection 尝试，防止 Agent 被诱导产生幻觉
```

### 4.4 收敛策略：自反馈纠错机制

#### 4.4.1 Retry-Lesson-Capture（重试经验捕获）

这是 miniOpenClaw 最独特的收敛机制。当一个任务在首次尝试失败、重试成功时，系统自动将"失败原因 → 成功方法"的映射持久化：

```
失败尝试 → 诊断原因 → 成功重试 → 经验捕获
                                    ├── 写入 workspace/MEMORY.md（跨会话持久化）
                                    └── 写入当前 SKILL.md（技能级持久化）
```

下次遇到类似任务时，Agent 会读取这些经验，避免重复犯错。这是一种**确定性收敛**——系统的行为随着使用次数增加而趋向稳定。

#### 4.4.2 Wiki Lint 自动修复闭环

```
知识入库 → LintWikiTool 检测问题
    ├── 缺失 frontmatter → 自动补全
    ├── 无效 status → 自动修正
    ├── 索引不匹配 → 自动重建
    └── 缺失实体页 → backfill 模式 LLM 提取补全
```

每日消化流水线的最后一步就是 Post-Digest Lint：`LintWikiTool(auto_fix=True, backfill=True)`，确保批量入库后知识图谱的结构完整性。

#### 4.4.3 对话历史压缩的收敛效果

`SummarizationMiddleware` 在消息数达到阈值时压缩对话历史，本质上是一种**信息熵压缩**——将分散在多轮对话中的信息收敛为结构化摘要，同时保留关键目标和产出物。

### 4.5 确定性路径控制的实现

系统通过三个机制实现确定性路径控制：

**1. 工具注册白名单**：`tools/__init__.py` 中显式注册所有可用工具，Agent 只能调用已注册的工具，无法"发明"新工具。

**2. 前置条件检查**：每个 Skill 的步骤之间有隐式依赖——Step 5（创建实体页）依赖 Step 4（论文页创建成功），Step 10（重建索引）依赖 Step 1-9 的所有写入完成。

**3. 输出格式约束**：Wiki 页使用 YAML frontmatter 强制结构化输出，8 种实体类型各有 schema。`LintWikiTool` 验证输出是否符合 schema，不符合则标记为异常。

### 4.6 稳定性度量

`HarnessReviewMiddleware` 在每轮对话后生成结构化审查报告：

```json
{
  "quality_score": 8,
  "hallucination_risk": "low",
  "issues": [],
  "tool_audit": [
    {"tool": "query_wiki", "appropriate": true},
    {"tool": "save_wiki_page", "appropriate": true}
  ],
  "summary": "回答准确引用了 3 个 Wiki 页面，无幻觉风险"
}
```

这个审查结果可以被外部监控系统（如 Langfuse）聚合分析，形成 Agent 行为的长期稳定性画像。

---

## 五、总结：架构哲学

miniOpenClaw 学术研究 Agent 的设计可以概括为一句话：

> **在宏观层面用确定性约束抑制熵增，在微观层面保留推理灵活性，在事后用自反馈机制实现收敛。**

具体表现为：
- **Skill-Guided Plan-and-Execute**：声明式任务拆解 + ReAct 执行
- **三层记忆金字塔**：L0 原始消息 → L1 原子事实 → L2 场景 → L3 人格
- **五层中间件安全链**：Guardian → Security → Offload → Summarization → Review
- **六重幻觉防线**：从价值观到底层工具的全链路防护
- **自反馈收敛**：retry-lesson-capture + lint auto-fix + banlist 反重复

这套架构确保了 Agent 在长链推理中保持有序度，同时通过持续的经验积累实现"越用越好"的正向循环。
