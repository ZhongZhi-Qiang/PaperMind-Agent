## 1. 核心概念：什么是 Function Calling

Function Calling 是 OpenAI 在 2023 年引入的能力，让 LLM 不再只能输出自由文本，而是可以**结构化地调用外部函数**。

**传统 LLM 交互：**
```
用户: 帮我查一下北京的天气
LLM:  抱歉，我无法访问实时天气数据...（纯文本回复）
```

**Function Calling 交互：**
```
用户: 帮我查一下北京的天气
LLM:  我需要调用工具 → {name: "get_weather", args: {city: "北京"}}
系统: 执行 get_weather("北京") → {"temp": 22, "condition": "晴"}
LLM:  北京现在 22°C，天气晴朗。
```

LLM 的角色从"回答者"变成了"决策者"——它决定**调用哪个工具**、**传什么参数**，但不执行工具本身。

## 2. 一个完整的例子：从定义到调用

### 2.1 第一步：用 Python 定义工具

以 miniOpenClaw 中的记忆搜索工具为例：

```python
# backend/memory_module_v3/integrations/tools.py

@tool
def search_memory(
    query: str,
    mode: str = "hybrid_cross",
    top_k: int = 5,
    session_ids: Optional[str] = None,
) -> str:
    """搜索跨会话的长期记忆，查找与当前问题相关的历史对话片段。
    默认搜索所有历史 session（跨 session 长期记忆）。
    当用户提到过去讨论过的话题、之前解决过的问题时，调用此工具。

    Args:
        query: 搜索查询，描述你要查找的内容。
        mode: 检索模式 - "hybrid_cross"（默认推荐）、"dense_distilled" 或 "keyword_verbatim"。
        top_k: 返回结果数量（默认 5）。
        session_ids: 按 session ID 过滤（逗号分隔，可选）。
    """
    # ... 实际执行逻辑
```

关键要素：
- **函数签名**：参数类型注解（`str`, `int`, `Optional[str]`）→ 生成 JSON Schema
- **docstring**：Google 风格文档 → 提取参数描述，成为 LLM 的决策依据
- **`@tool` 装饰器**：将普通函数包装为 LangChain 的 `StructuredTool`

### 2.2 第二步：LangChain 自动生成 JSON Schema

`@tool` 装饰器内部调用链：

```
@tool
  → StructuredTool.from_function(func, infer_schema=True)
    → create_schema_from_function()
      → pydantic.validate_arguments(func)  # Pydantic 分析函数签名
      → _infer_arg_descriptions(func)       # 从 docstring 提取参数描述
      → _create_subset_model()              # 构建 Pydantic BaseModel 子类
```

最终生成的 JSON Schema（这就是发送给 LLM API 的 `tools` 参数）：

```json
{
  "type": "function",
  "function": {
    "name": "search_memory",
    "description": "搜索跨会话的长期记忆，查找与当前问题相关的历史对话片段。",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {
          "type": "string",
          "description": "搜索查询，描述你要查找的内容。"
        },
        "mode": {
          "type": "string",
          "default": "hybrid_cross",
          "description": "检索模式 - hybrid_cross / dense_distilled / keyword_verbatim"
        },
        "top_k": {
          "type": "integer",
          "default": 5,
          "description": "返回结果数量"
        },
        "session_ids": {
          "type": "string",
          "description": "按 session ID 过滤（逗号分隔，可选）"
        }
      },
      "required": ["query", "mode", "top_k"]
    }
  }
}
```

### 2.3 第三步：发送给 LLM API

实际的 HTTP 请求（由 LangChain 的 `ChatOpenAI` 自动构造）：

```json
{
  "model": "gpt-4o",
  "messages": [
    {"role": "system", "content": "你是一个学术研究助手..."},
    {"role": "user", "content": "我们之前讨论过 RAG 的局限性吗？"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "search_memory",
        "description": "搜索跨会话的长期记忆...",
        "parameters": { "..." }
      }
    },
    {
      "type": "function",
      "function": {
        "name": "pdf_parser",
        "description": "Parse an academic PDF paper...",
        "parameters": { "..." }
      }
    }
    // ... 其他 13+ 个工具
  ]
}
```

LLM 收到的上下文：**系统提示 + 用户消息 + 所有可用工具的 schema**。

### 2.4 第四步：LLM 返回 tool_calls

LLM 分析用户意图后，返回结构化的工具调用请求：

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [
        {
          "id": "call_abc123",
          "type": "function",
          "function": {
            "name": "search_memory",
            "arguments": "{\"query\": \"RAG 局限性\", \"mode\": \"hybrid_cross\", \"top_k\": 5}"
          }
        }
      ]
    }
  }]
}
```

注意：
- `content` 为 `null` —— LLM 没有生成文本回复，而是决定调用工具
- `arguments` 是 **JSON 字符串**（不是对象），需要解析
- LLM **自主选择**调用哪个工具、传什么参数，依据是 schema 中的 `description`

### 2.5 第五步：执行工具并返回结果

LangChain 的 `ToolNode` 自动处理：

```python
# LangChain 内部流程（简化）
tool_call = {"name": "search_memory", "args": {"query": "RAG 局限性", ...}}
tool = tools_by_name["search_memory"]          # 按 name 查找工具
validated_args = tool.args_schema.model_validate(tool_call["args"])  # Pydantic 校验
result = tool._run(**validated_args)             # 执行实际函数
# 返回 ToolMessage
```

结果以 `ToolMessage` 追加到消息列表：

```json
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "name": "search_memory",
  "content": "[#1] session=a3f2c1… ply=12-15 score=0.892\n用户之前讨论了 RAG 的三个主要局限性..."
}
```

### 2.6 第六步：LLM 基于工具结果生成最终回复

消息历史现在是：

```
[system]  你是一个学术研究助手...
[user]    我们之前讨论过 RAG 的局限性吗？
[assistant] tool_calls: [{name: "search_memory", args: {...}}]
[tool]    [#1] session=a3f2c1… 用户之前讨论了 RAG 的三个主要局限性...
```

LLM 看到工具结果后，生成最终文本回复：

```
是的，我们之前讨论过 RAG 的三个主要局限性：
1. 检索精度依赖 embedding 质量
2. 长文档切分导致上下文丢失
3. 无法处理需要多跳推理的问题
```

## 3. Pydantic 原理：数据校验与 Schema 生成

Pydantic 是整个工具调用链路的基石——它同时负责**数据校验**和 **JSON Schema 生成**。

### 3.1 Pydantic 的核心机制

```python
from pydantic import BaseModel, Field
from typing import Literal

class GuardianOutput(BaseModel):
    label: Literal["安全", "危险"] = Field(description="安全分类结果")
    reason: str = Field(default="", description="分类理由")
```

当你定义一个 Pydantic 模型时，Pydantic 在**类创建阶段**（不是实例化阶段）就完成了：

```
Python 类定义
    │
    ▼
Pydantic ModelMetaclass.__new__()
    │
    ├─→ 解析类型注解（str, int, Literal, Optional, list, 嵌套 BaseModel...）
    ├─→ 提取 Field() 元信息（description, default, ge, le...）
    ├─→ 生成核心 Schema（CoreSchema）—— 一个中间表示
    ├─→ 编译验证器（pydantic-core，Rust 实现，极快）
    └─→ 注册 model_json_schema() 方法
```

### 3.2 Pydantic 如何生成 JSON Schema

```python
>>> GuardianOutput.model_json_schema()
{
    "properties": {
        "label": {
            "description": "安全分类结果",
            "enum": ["安全", "危险"],
            "title": "Label",
            "type": "string"
        },
        "reason": {
            "default": "",
            "description": "分类理由",
            "title": "Reason",
            "type": "string"
        }
    },
    "required": ["label"],
    "title": "GuardianOutput",
    "type": "object"
}
```

生成过程：

```
BaseModel 子类
    │
    ▼
model_json_schema()
    │
    ├─→ 遍历 __fields__（所有字段的 FieldInfo）
    │     ├─ str → {"type": "string"}
    │     ├─ int → {"type": "integer"}
    │     ├─ float → {"type": "number"}
    │     ├─ bool → {"type": "boolean"}
    │     ├─ list[T] → {"type": "array", "items": <T 的 schema>}
    │     ├─ Literal["a", "b"] → {"type": "string", "enum": ["a", "b"]}
    │     ├─ Optional[T] → <T 的 schema>（不加 required）
    │     └─ 嵌套 BaseModel → {"$ref": "#/$defs/ModelName"}
    │
    ├─→ 从 Field() 提取元信息
    │     ├─ description → 加入 schema
    │     ├─ default / default_factory → 标记非 required
    │     ├─ ge/le/gt/lt → 加入 minimum/maximum
    │     └─ pattern → 加入正则约束
    │
    └─→ 生成最终 JSON Schema（draft-2020-12 格式）
```

### 3.3 Pydantic 如何校验数据

```python
# 校验通过
result = GuardianOutput.model_validate({"label": "安全", "reason": "正常对话"})
# → GuardianOutput(label="安全", reason="正常对话")

# 校验失败 —— 抛出 ValidationError
result = GuardianOutput.model_validate({"label": "不确定"})
# → ValidationError: Input should be '安全' or '危险'

# 类型强转（Pydantic 的"宽松模式"）
result = GuardianOutput.model_validate({"label": "安全", "reason": 123})
# → GuardianOutput(label="安全", reason="123")  # int 被转为 str
```

校验流程：

```
输入数据（dict / JSON）
    │
    ▼
model_validate()
    │
    ├─→ pydantic-core（Rust）执行验证
    │     ├─ 检查 required 字段是否存在
    │     ├─ 按类型注解校验每个字段
    │     ├─ Literal → 检查值是否在枚举中
    │     ├─ ge/le → 检查数值范围
    │     └─ 嵌套模型 → 递归校验
    │
    ├─→ 失败 → ValidationError（包含每个字段的错误详情）
    └─→ 成功 → 返回模型实例（Python 对象，支持 .label, .reason 属性访问）
```

### 3.4 Pydantic v2 的性能优势

Pydantic v2 的核心验证器用 Rust 实现（`pydantic-core`），比 v1 快 **5-50 倍**：

```
Pydantic v1: Python 循环逐字段验证 → 慢
Pydantic v2: Rust 编译验证器 → 快

Schema 生成也从 v1 的运行时推断变为 v2 的类创建时编译，开销接近零。
```

## 4. LangChain 工具调用底层原理

### 4.1 工具定义层：三种方式

| 方式 | 示例 | Schema 来源 |
|------|------|-------------|
| `@tool` 装饰器 | `@tool\ndef fn(q: str) -> str: """desc"""` | 从函数签名 + docstring 自动推断 |
| `BaseTool` 子类 | `class MyTool(BaseTool): args_schema = MyInput` | 显式指定 `args_schema`（Pydantic 模型） |
| 纯 dict | `{"type": "function", "function": {...}}` | 手写 JSON Schema，直接透传 |

miniOpenClaw 中两种方式都用了：

```python
# 方式 1：@tool 装饰器（memory 工具）
@tool
def search_memory(query: str, mode: str = "hybrid_cross") -> str:
    """搜索跨会话记忆..."""

# 方式 2：BaseTool 子类（PDF 解析工具）
class PDFParserTool(BaseTool):
    name: str = "pdf_parser"
    description: str = "Parse an academic PDF..."
    args_schema: Type[BaseModel] = PDFParserInput  # 显式 Pydantic 模型
```

### 4.2 Schema 转换层：Python → JSON Schema → OpenAI 格式

转换链路：

```
BaseTool / @tool / Pydantic 模型
    │
    ▼
convert_to_openai_tool(tool)
    │
    ├─→ 如果是 BaseTool：
    │     tool.tool_call_schema → _convert_pydantic_to_openai_function()
    │       → model.model_json_schema()           # Pydantic 生成 JSON Schema
    │       → dereference_refs(schema)             # 解析 $ref 引用
    │       → _rm_titles(schema)                   # 移除冗余 title 字段
    │       → {"name": ..., "description": ..., "parameters": {...}}
    │
    ├─→ 如果是 @tool 装饰器：
    │     args_schema（自动生成的 Pydantic 模型）→ 同上
    │
    └─→ 如果是 dict：
          直接透传（已经是 OpenAI 格式）
    │
    ▼
{
  "type": "function",
  "function": {
    "name": "tool_name",
    "description": "...",
    "parameters": { "type": "object", "properties": {...}, "required": [...] }
  }
}
```

### 4.3 模型绑定层：`bind_tools`

```python
# ChatOpenAI.bind_tools() 的核心逻辑
def bind_tools(self, tools, tool_choice=None, **kwargs):
    formatted_tools = [convert_to_openai_tool(tool) for tool in tools]
    # tool_choice 处理
    if isinstance(tool_choice, str):
        if tool_choice == "any":
            tool_choice = "required"
        elif tool_choice not in ("auto", "none", "required"):
            tool_choice = {"type": "function", "function": {"name": tool_choice}}
    return self.bind(tools=formatted_tools, tool_choice=tool_choice, **kwargs)
```

`self.bind()` 创建一个 `_ChatModelBinding` Runnable——它不立即调用 API，而是在 `invoke()` 时将 `tools` 参数注入到 API 请求中。

### 4.4 Agent 循环层：`create_agent`

`create_agent` 构建一个 LangGraph 状态图：

```
┌─────────────────────────────────────────────────────┐
│                     Agent Graph                      │
│                                                      │
│  START                                               │
│    │                                                 │
│    ▼                                                 │

│    │                                                 │
│    ▼                                                 │
│  ┌──────────────────────┐                            │
│  │     model 节点        │ ← LLM 推理                 │
│  │  (bind_tools 后的     │                            │
│  │   ChatOpenAI.invoke)  │                            │
│  └──────┬───────────────┘                            │
│         │                                            │

│  [ContextOffloadMiddleware.before_model]              │
```

### 4.5 工具执行层：ToolNode

```python
# LangGraph 的 ToolNode 内部逻辑（简化）
class ToolNode:
    def invoke(self, input):
        for tool_call in input["messages"][-1].tool_calls:
            # 1. 按 name 查找工具
            tool = self.tools_by_name[tool_call["name"]]

            # 2. Pydantic 校验参数
            #    BaseTool._parse_input() 内部：
            #    args_schema.model_validate(tool_call["args"])

            # 3. 执行工具
            output = tool.invoke(tool_call)

            # 4. 包装为 ToolMessage
            result.append(ToolMessage(
                content=str(output),
                tool_call_id=tool_call["id"],
                name=tool_call["name"],
            ))
        return {"messages": result}
```

## 5. with_structured_output：强制 LLM 输出结构化数据

### 5.1 问题：LLM 默认输出自由文本

```python
llm.invoke("分析这段对话的质量，输出 JSON")
# LLM 可能返回：
# "好的，这是分析结果：\n```json\n{...}\n```\n希望对你有帮助！"
# 你需要正则提取 JSON，处理各种边界情况...
```

### 5.2 解决方案：with_structured_output

```python
from pydantic import BaseModel, Field
from typing import Literal

class ReviewOutput(BaseModel):
    quality_score: int = Field(ge=1, le=10)
    hallucination_risk: Literal["low", "medium", "high"]
    summary: str

structured_llm = llm.with_structured_output(ReviewOutput)
result = structured_llm.invoke("分析这段对话的质量")
# result 是 ReviewOutput 实例，不是字符串！
print(result.quality_score)  # 8
print(result.hallucination_risk)  # "low"
```

### 5.3 底层实现：三种策略

`with_structured_output()` 有三种实现策略：

#### 策略 1：Function Calling（默认）

要调用工具的时候，也知道对应工具的schema，相当于会执行这个工具，llm 的输出被限制在 schema 定义的参数结构内。限制底层原理的话，可能是token生成的时候加上了约束解码，只能在符合约束的条件下采样路径。


```python
# LangChain 内部实现（简化）
def with_structured_output(self, schema, method="function_calling"):
    tool_name = convert_to_openai_tool(schema)["function"]["name"]
    llm = self.bind_tools([schema], tool_choice=tool_name, parallel_tool_calls=False)
    parser = PydanticToolsParser(tools=[schema], first_tool_only=True)
    return llm | parser
```

原理：
1. 将 Pydantic schema **伪装成一个工具**
2. 设置 `tool_choice=tool_name` —— **强制** LLM 调用这个"工具"
3. LLM 的输出被限制在 schema 定义的参数结构内
4. `PydanticToolsParser` 将 tool_call 的 args 解析为 Pydantic 对象

```
LLM API 请求：
{
  "tools": [{
    "type": "function",
    "function": {
      "name": "ReviewOutput",
      "parameters": {
        "quality_score": {"type": "integer", "minimum": 1, "maximum": 10},
        "hallucination_risk": {"type": "string", "enum": ["low", "medium", "high"]},
        "summary": {"type": "string"}
      }
    }
  }],
  "tool_choice": {"type": "function", "function": {"name": "ReviewOutput"}}
  //       ↑ 强制调用，LLM 没有其他选择
}

LLM 返回：
{
  "tool_calls": [{
    "function": {
      "name": "ReviewOutput",
      "arguments": "{\"quality_score\": 8, \"hallucination_risk\": \"low\", \"summary\": \"回答准确\"}"
    }
  }]
}

解析后：
ReviewOutput(quality_score=8, hallucination_risk="low", summary="回答准确")
```

#### 策略 2：JSON Schema（OpenAI Structured Outputs）

```python
def with_structured_output(self, schema, method="json_schema"):
    response_format = {
        "type": "json_schema",
        "json_schema": {
            "name": "ReviewOutput",
            "schema": schema.model_json_schema(),
            "strict": True
        }
    }
    llm = self.bind(response_format=response_format)
    parser = PydanticOutputParser(pydantic_object=schema)
    return llm | parser
```

原理：使用 OpenAI 原生的 `response_format` 参数，在 **token 生成层面**约束输出格式。比 Function Calling 更严格——LLM **不可能**输出不符合 schema 的 JSON。

#### 策略 3：JSON Mode

```python
def with_structured_output(self, schema, method="json_mode"):
    llm = self.bind(response_format={"type": "json_object"})
    parser = PydanticOutputParser(pydantic_object=schema)
    return llm | parser
```

原理：只约束输出为合法 JSON，不约束结构。需要事后用 Pydantic 校验。最宽松但兼容性最好。

### 5.4 三种策略对比

| 策略 | 约束强度 | 兼容性 | 原理 |
|------|---------|--------|------|
| `function_calling` | 强 | 所有支持 function calling 的模型 | 把 schema 伪装成工具，强制调用 |
| `json_schema` | 最强 | 仅 OpenAI gpt-4o 等 | Token 级别约束，不可能输出错误格式 |
| `json_mode` | 弱 | 所有支持 JSON mode 的模型 | 只约束为合法 JSON，不约束结构 |

miniOpenClaw 使用的是默认的 `function_calling` 策略，因为它兼容所有 OpenAI 兼容 API（智谱、百炼、DeepSeek 等）。

## 6. Schema 设计原则

### 6.1 字段设计

```python
# 好的设计：明确的类型 + 描述 + 约束
class ReviewOutput(BaseModel):
    quality_score: int = Field(
        ge=1, le=10,                    # 数值约束：LLM 不会输出 0 或 11
        description="回答质量评分，1-10"
    )
    hallucination_risk: Literal["low", "medium", "high"] = Field(
        description="幻觉风险等级"        # Literal = 枚举，LLM 只能三选一
    )
    issues: list[ReviewIssue] = Field(
        default_factory=list,            # 默认空列表，LLM 可以不填
        description="发现的问题列表"
    )

# 差的设计：宽松的类型
class ReviewOutput(BaseModel):
    quality_score: int              # 没有 ge/le，LLM 可能输出 100
    risk: str                       # 没有 Literal，LLM 可能输出 "中等风险"
    issues: list                    # 没有指定元素类型
```

### 6.2 用 Literal 约束枚举值

```python
# Literal 是最强大的约束工具
label: Literal["安全", "危险"]     # LLM API 层面强制二选一
severity: Literal["low", "medium", "high"]  # 三选一
type: Literal["tool_misuse", "inaccuracy", "hallucination", "omission"]  # 四选一
```

对应 JSON Schema 中的 `"enum"` 字段，LLM 在生成 token 时只能从给定选项中选择。

### 6.3 嵌套模型

```python
class ToolAuditDetail(BaseModel):
    tool: str
    appropriate: bool
    reason: str = ""

class ToolAudit(BaseModel):
    total_calls: int = 0
    details: list[ToolAuditDetail] = []  # 嵌套模型

class ReviewOutput(BaseModel):
    tool_audit: ToolAudit  # 两层嵌套
```

嵌套模型会被递归转换为 JSON Schema：

```json
{
  "tool_audit": {
    "type": "object",
    "properties": {
      "total_calls": {"type": "integer"},
      "details": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "tool": {"type": "string"},
            "appropriate": {"type": "boolean"},
            "reason": {"type": "string"}
          }
        }
      }
    }
  }
}
```

### 6.4 description 是 LLM 的唯一线索

```python
# description 直接影响 LLM 的决策质量
query: str = Field(description="搜索查询，描述你要查找的内容")
# LLM 看到这个 description 后，知道要填一个描述性的搜索词

query: str = Field(description="query")
# LLM 不知道该填什么，可能填一个无意义的字符串
```

**规则：每个字段都必须有 description，它是 LLM 理解"该填什么"的唯一依据。**

## 7. 完整链路图

### 7.1 工具调用全链路

```
┌─────────────────────────────────────────────────────────────┐
│                    工具调用全链路                              │
│                                                              │
│  ① 定义层                                                    │
│  Python 函数 + @tool 装饰器 / BaseTool 子类                   │
│  ├── 类型注解 (str, int, Literal, Optional)                   │
│  ├── docstring (Google 风格，Args 描述)                       │
│  └── Field() 元信息 (ge/le, description, default)             │
│       │                                                      │
│       ▼                                                      │
│  ② Schema 生成层                                             │
│  @tool → StructuredTool.from_function()                      │
│  ├── pydantic.validate_arguments(func) → 推断类型             │
│  ├── _infer_arg_descriptions() → 提取 docstring 描述         │
│  └── _create_subset_model() → 生成 Pydantic BaseModel        │
│       │                                                      │
│       ▼                                                      │
│  ③ API 格式转换层                                             │
│  convert_to_openai_tool(tool)                                │
│  ├── model.model_json_schema() → JSON Schema                 │
│  ├── dereference_refs() → 解析 $ref                          │
│  └── 输出 OpenAI function calling 格式                        │
│       │                                                      │
│       ▼                                                      │
│  ④ 模型绑定层                                                 │
│  model.bind_tools([tool1, tool2, ...])                       │
│  └── 创建 _ChatModelBinding Runnable                         │
│       │                                                      │
│       ▼                                                      │
│  ⑤ API 调用层                                                 │
│  model.invoke(messages, tools=[...])                         │
│  └── HTTP POST → OpenAI / 智谱 / 百炼 / DeepSeek API         │
│       │                                                      │
│       ▼                                                      │
│  ⑥ LLM 决策层                                                │
│  LLM 分析用户意图 + 工具 schema → 输出 tool_calls             │
│  └── {name: "search_memory", args: {query: "...", ...}}      │
│       │                                                      │
│       ▼                                                      │
│  ⑦ 安全拦截层 (HarnessSecurityMiddleware)                     │
│  └── 检查工具名 + 参数是否匹配危险规则                         │
│       │                                                      │
│       ▼                                                      │
│  ⑧ 工具执行层 (ToolNode)                                     │
│  ├── tools_by_name[tool_name] → 查找工具                     │
│  ├── args_schema.model_validate(args) → Pydantic 校验参数     │
│  ├── tool._run(**validated_args) → 执行实际函数               │
│  └── 返回 ToolMessage(content=result)                        │
│       │                                                      │
│       ▼                                                      │
│  ⑨ 结果回传层                                                │
│  ToolMessage 追加到消息列表 → 回到 ⑤ 下一轮推理               │
│  └── 直到 LLM 不再调用工具，输出最终文本回复                   │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 结构化输出全链路

```
┌─────────────────────────────────────────────────────────────┐
│                 结构化输出全链路                               │
│                                                              │
│  ① 定义输出 Schema                                           │
│  class ReviewOutput(BaseModel):                              │
│      quality_score: int = Field(ge=1, le=10)                 │
│      hallucination_risk: Literal["low", "medium", "high"]    │
│       │                                                      │
│       ▼                                                      │
│  ② with_structured_output(ReviewOutput)                      │
│  ├── convert_to_openai_tool(ReviewOutput)                    │
│  │   → {"function": {"name": "ReviewOutput", "parameters": {...}}}│
│  ├── bind_tools([ReviewOutput], tool_choice="ReviewOutput")  │
│  │   → 强制 LLM 调用这个"工具"                                │
│  └── | PydanticToolsParser(tools=[ReviewOutput])             │
│       │                                                      │
│       ▼                                                      │
│  ③ API 调用                                                  │
│  structured_llm.invoke(messages)                             │
│  └── LLM 返回 tool_calls: [{name: "ReviewOutput", args: {...}}]│
│       │                                                      │
│       ▼                                                      │
│  ④ 解析                                                      │
│  PydanticToolsParser.parse_result()                          │
│  ├── 提取 tool_call["arguments"] → dict                      │
│  ├── ReviewOutput(**args) → Pydantic 校验 + 实例化            │

│       │                                                      │
│       ▼                                                      │
│  ⑤ 使用                                                      │
│  result = structured_llm.invoke(...)                         │
│  result.quality_score    # 8                                 │
│  result.hallucination_risk  # "low"                          │
│  result.model_dump()     # → {"quality_score": 8, ...}       │
└─────────────────────────────────────────────────────────────┘
```
